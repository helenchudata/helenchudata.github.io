Project Summary

LetsMeet Membership and Event Analysis

LetsMeet is a fictional platform that helps people find local groups and attend events in New York, Chicago, and San Francisco. The project reviews its six-table relational database to understand how Sales, Engineering, and leadership could report on membership, event activity, and venue use.

I reviewed the table definitions and sample records, identified what each row represents, and traced how groups connect memberships, events, categories, and cities. I then wrote MySQL queries to explore membership, report on events and growth, and restructure the membership data.

Skills and What I Learned

  • MySQL
  • Relational schemas
  • Data modeling
  • Reporting requirements

The LetsMeet schema helped me understand how related tables support reporting. A member can appear in several groups, so counting membership rows and counting distinct people answer different questions.

Findings from the Schema Review

  • Memberships and people are different measures. Each grp_member row represents one person’s membership in one group. Counting rows measures memberships. Counting distinct member_id values measures people.
  • Events can be compared by group, category, and venue. The event table links to the group and venue tables. Groups link to categories and cities, making it possible to compare event activity across interests and locations.
  • RSVPs and headcount describe different aspects of engagement. The event table lists yes RSVPs, maybe RSVPs, waitlist counts, and headcount separately. Confirming how each field is recorded would help distinguish interest from attendance.
  • City and venue data support local reporting. Venue addresses and coordinates help locate events. The case study flags the city table for cleaning, so I would validate city records and group-to-city matches before comparing markets.

The three project parts below show how the SQL labs applied this schema to reporting and database design. The figures come from the saved lab notes.

    city

	city,
    COUNT(event_id) AS total_events

JOIN city ON grp.city_id = city.city_id

Membership growth

Download membership growth (.sql)

-- The growth of LetsMeet over the years based on the number of members who joined each year
SELECT 
	join_yr,
    COUNT(join_yr)
FROM
	(SELECT member_id, YEAR(MIN(joined)) AS join_yr
    FROM grp_member
GROUP BY member_id) AS yr
GROUP BY join_yr
ORDER BY join_yr DESC; 
    
-- Rename the smaller cities to the name of their larger urban areas Chicago, San Francisco, and/or New York
SET SQL_SAFE_UPDATES = 0;

UPDATE grp_member
	SET city = "Chicago"
WHERE city IN ("East Chicago", "West Chicago", "North Chicago", "Chicago Heights", "Chicago Ridge");

UPDATE grp_member
	SET city = "San Francisco"
WHERE city IN ("South San Francisco");

UPDATE grp_member
	SET city = "New York"
WHERE city IN ("West New York");

-- Query break down groups by rating
SELECT 
	CASE
		WHEN rating BETWEEN 1 AND 1.99 THEN "1-1.99"
        WHEN rating BETWEEN 2 AND 2.99 THEN "2-2.99"
        WHEN rating BETWEEN 3 AND 3.99 THEN "3-3.99"
        WHEN rating BETWEEN 4 AND 4.99 THEN "4-4.99"
        WHEN rating = 5 THEN "5"
	END AS rating_category,
    COUNT(group_id) AS group_count
FROM grp
GROUP BY rating_category
ORDER BY rating_category;

Part 3 · Normalizing Data

I split the original membership table into member records and group sign-ups, linked them with foreign keys, and removed selected redundant fields. The MySQL Workbench model shows the revised relationships.

Normalization script

Download normalization script (.sql)

-- Eliminate redundant columns
ALTER TABLE venue_ 
DROP COLUMN country;
/*The country column in the venue_ table is already present in the city table*/

ALTER TABLE city
DROP COLUMN distance; 
/*The distance column in the city table is uniformative*/

ALTER TABLE event
DROP COLUMN why;
/*The why column in the event table don't add additional value to the data*/

ALTER TABLE category
DROP COLUMN sort_name;
/*The sort_name column in the category table contains repetitive information*/

ALTER TABLE grp_member
DROP COLUMN country;
/* The country column in the grp_member table is redundant because LetsMeet only 
operates in one country*/

-- Split grp_member table
CREATE TABLE group_sign_ups
SELECT DISTINCT group_id, member_id, joined
FROM grp_member;

CREATE TABLE members
SELECT DISTINCT member_id, member_name, city, hometown, member_status
FROM grp_member;

ALTER TABLE members
ADD PRIMARY KEY (member_id);

ALTER TABLE group_sign_ups
ADD FOREIGN KEY (member_id) REFERENCES members(member_id);

ALTER TABLE group_sign_ups
ADD FOREIGN KEY (group_id) REFERENCES grp(group_id);

DROP TABLE grp_member;
